# URL Shortener + Agentic SDLC Orchestrator

**Repository:** https://github.com/kcpkash888/url-shortener-agentic-assignment

A working URL shortener service (Java 21 + Spring Boot), plus a from-scratch
agentic orchestration engine that used itself to build three real features
into that service (greenfield, brownfield, and an ambiguous requirement),
producing an audit trail, decision lineage, and reliability metrics for
each run.

Read [ARCHITECTURE.md](ARCHITECTURE.md) for how the orchestrator works,
[SCENARIOS.md](SCENARIOS.md) for a walkthrough of the three demo runs,
[TESTING.md](TESTING.md) for the test approach and known limitations, and
[SUMMARY.md](SUMMARY.md) for the final engineering summary (plan, risks,
assumptions).

## Project layout

```
src/main/java/com/example/urlshortener/
  app/                the URL shortener service (Spring Boot)
    dto/                 request/response records
    exceptions/          domain exceptions + GlobalExceptionHandler mapping them to HTTP status
  orchestrator/         the agentic orchestration engine (framework, not app-specific)
    Graph.java, Node.java        dependency graph: nodes, waves, staleness/re-planning
    Executor.java                walks the graph: gates, retries, fallback, rollback, safe-stop
    SharedContext.java           shared state + decision lineage across a run
    Policies.java                guardrail policies (secrets, dependency allowlist, tests-must-pass, release gate)
    Approver.java, AutoApprover.java   human approval checkpoint interface + demo auto-approver
    EventLog.java                append-only structured event log (the audit trail)
    MetricsCalculator.java       reliability metrics computed from the event log
    agents/                      the "SDLC agents" the graph nodes call: requirements, design,
                                  codebase-analysis, implementation, testing, docs, release
  scenarios/           the three demo scenarios, runnable end to end
    GreenfieldRun.java   adds a brand-new capability (bulk link creation)
    BrownfieldRun.java   enhances existing code + re-plans + a security rollback/recovery
    AmbiguousRun.java    resolves an underspecified request, then implements it
    ResetDemoState.java  restores src/main/java/.../app/ to its pre-scenario baseline (see below)
src/test/java/...      the test suite (JUnit 5 / Spring Boot Test)
src/main/resources/    application.properties, schema.sql
runs/                  generated per-run audit logs + Markdown reports (git-ignorable)
docs/                  API_CHANGELOG.md, generated by the docs agent as scenarios run
```

## Setup

Requires **Java 21+** and **Maven 3.9+**. No external services, no API keys,
no IDE required.

```bash
mvn install
```

## Run the service

```bash
mvn spring-boot:run
```

or build and run the jar directly:

```bash
mvn package -DskipTests
java -jar target/urlshortener-agentic.jar
```

Then, for example:

```bash
curl -X POST http://localhost:8080/api/urls -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/some/long/path"}'
curl -i http://localhost:8080/<code>
curl http://localhost:8080/api/urls/<code>/analytics
```

## Run the tests

```bash
mvn test
```

## Run the orchestrated scenarios

Each scenario is a standalone `main()` that builds a dependency graph, runs
the orchestrator against the real codebase in this repo (it writes real
`.java` files, runs the real `mvn test` suite, and can really roll a change
back), and writes a report to `runs/<run-id>/REPORT.md` plus a full event
trace to `runs/<run-id>/events.jsonl`.

```bash
mvn exec:java -Dexec.mainClass=com.example.urlshortener.scenarios.GreenfieldRun
mvn exec:java -Dexec.mainClass=com.example.urlshortener.scenarios.BrownfieldRun
mvn exec:java -Dexec.mainClass=com.example.urlshortener.scenarios.AmbiguousRun
```

Run them in that order the first time -- brownfield and ambiguous build on
top of what greenfield adds (bulk link creation), and brownfield's second
half deliberately triggers a policy-guardrail rollback before recovering.

**To replay the scenarios from a clean baseline** (e.g. to re-run them a
second time and see the same diffs again), reset the working tree first:

```bash
mvn exec:java -Dexec.mainClass=com.example.urlshortener.scenarios.ResetDemoState
```

This restores `UrlController.java`, `GlobalExceptionHandler.java`,
`AnalyticsResponse.java`, and `ShortenerService.java` to their pre-scenario
state, removes the files the scenarios generated, and clears
`docs/API_CHANGELOG.md` and `runs/`. See [SCENARIOS.md](SCENARIOS.md) for
why the scenarios aren't simply idempotent against an already-mutated
codebase -- it's a deliberate guardrail, not a bug.

## What's real vs. simulated

Everything the orchestrator does to the codebase is real: it reads the
actual files in `src/main/java/.../app/`, writes real file content, runs
the real `mvn test` build+test cycle as a subprocess (which also means a
compile error is a real, orchestrator-visible failure, not just a test
failure), and reverts real file writes on rollback. What's necessarily
stood in for this prototype: the "agents" are deterministic Java functions
rather than LLM calls (see
[ARCHITECTURE.md](ARCHITECTURE.md#agents-vs-llm-calls) for why, and how
they're designed to be swapped for real model calls), and the human
approval checkpoint is a policy-driven `AutoApprover` rather than a person
in a chat client (see
[ARCHITECTURE.md](ARCHITECTURE.md#approvals--human-checkpoints)) -- both
are explicitly called out where they appear, both plug into the same
interface a real implementation would use.
