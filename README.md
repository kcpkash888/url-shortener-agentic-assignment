# URL Shortener + Agentic SDLC Orchestrator

**Live demo:** https://url-shortener-agentic-assignment.onrender.com/docs
(interactive Swagger UI — try `POST /api/urls`, then `GET /{code}`; free-tier
instance, so the first request after a period of inactivity can take up to
~50s to wake up).

**Repository:** https://github.com/kcpkash888/url-shortener-agentic-assignment

**Java port:** [`java/`](java/) is a behavior-preserving Java 21 + Spring
Boot rebuild of everything below -- same service, same orchestration
engine, same three scenarios. See [`java/README.md`](java/README.md).

A working URL shortener service, plus a from-scratch agentic orchestration
engine that used itself to build three real features into that service
(greenfield, brownfield, and an ambiguous requirement), producing an audit
trail, decision lineage, and reliability metrics for each run.

Read [ARCHITECTURE.md](ARCHITECTURE.md) for how the orchestrator works,
[SCENARIOS.md](SCENARIOS.md) for a walkthrough of the three demo runs,
[TESTING.md](TESTING.md) for the test approach and known limitations, and
[SUMMARY.md](SUMMARY.md) for the final engineering summary (plan, risks,
assumptions).

## Project layout

```
app/                the URL shortener service (FastAPI)
tests/               its test suite (pytest)
orchestrator/        the agentic orchestration engine (framework, not app-specific)
  graph.py             dependency graph: nodes, waves, staleness/re-planning
  executor.py          walks the graph: gates, retries, fallback, rollback, safe-stop
  context.py           shared state + decision lineage across a run
  policy.py            guardrail policies (secrets, dependency allowlist, tests-must-pass, release gate)
  approvals.py         human approval checkpoint interface + demo auto-approver
  observability.py     append-only structured event log (the audit trail)
  metrics.py           reliability metrics computed from the event log
  agents/              the "SDLC agents" the graph nodes call: requirements, design,
                       codebase-analysis, implementation, testing, docs, release
scenarios/            the three demo scenarios, runnable end to end
  greenfield_run.py     adds a brand-new capability (bulk link creation)
  brownfield_run.py     enhances existing code + re-plans + a security rollback/recovery
  ambiguous_run.py      resolves an underspecified request, then implements it
  reset_demo_state.py   restores app/ to its pre-scenario baseline (see below)
runs/                generated per-run audit logs + Markdown reports (git-ignorable)
docs/                API_CHANGELOG.md, generated by the docs agent as scenarios run
```

## Setup

Requires Python 3.11+ (developed on 3.13). No external services, no API keys.

```bash
pip install -r requirements.txt
```

## Run the service

```bash
python -m uvicorn app.main:app --reload
```

Then, for example:

```bash
curl -X POST http://localhost:8000/api/urls -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/some/long/path"}'
curl -i http://localhost:8000/<code>
curl http://localhost:8000/api/urls/<code>/analytics
```

Interactive API docs are at `http://localhost:8000/docs` (FastAPI's built-in
Swagger UI).

## Run the tests

```bash
python -m pytest tests/ -v
```

## Run the orchestrated scenarios

Each scenario is a standalone script that builds a dependency graph, runs
the orchestrator against the real codebase in this repo (it writes real
files, runs the real test suite, and can really roll a change back), and
writes a report to `runs/<run-id>/REPORT.md` plus a full event trace to
`runs/<run-id>/events.jsonl`.

```bash
python -m scenarios.greenfield_run     # add a brand-new endpoint
python -m scenarios.brownfield_run     # enhance existing code, re-plan, and recover from a rollback
python -m scenarios.ambiguous_run      # resolve an underspecified request, then implement it
```

Run them in that order the first time -- brownfield and ambiguous build on
top of what greenfield adds (bulk link creation), and brownfield's second
half deliberately triggers a policy-guardrail rollback before recovering.

**To replay the scenarios from a clean baseline** (e.g. to re-run them a
second time and see the same diffs again), reset the working tree first:

```bash
python -m scenarios.reset_demo_state
```

This restores `app/main.py`, `app/schemas.py`, and `app/shortener.py` to
their pre-scenario state, removes the files the scenarios generated, and
clears `docs/API_CHANGELOG.md` and `runs/`. See
[SCENARIOS.md](SCENARIOS.md) for why the scenarios aren't simply idempotent
against an already-mutated codebase -- it's a deliberate guardrail, not a
bug.

## What's real vs. simulated

Everything the orchestrator does to the codebase is real: it reads the
actual files in `app/`, writes real file content, runs the real `pytest`
suite as a subprocess, and reverts real file writes on rollback. What's
necessarily stood in for this prototype: the "agents" are deterministic
Python functions rather than LLM calls (see
[ARCHITECTURE.md](ARCHITECTURE.md#agents-vs-llm-calls) for why, and how
they're designed to be swapped for real model calls), and the human
approval checkpoint is a policy-driven `AutoApprover` rather than a person
in a chat client (see
[ARCHITECTURE.md](ARCHITECTURE.md#approvals--human-checkpoints)) -- both
are explicitly called out where they appear, both plug into the same
interface a real implementation would use.
